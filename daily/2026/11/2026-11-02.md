## 学到了什么

- **ACID 不该一起背，要拆到机制上**：undo 管回滚、redo 管崩溃恢复、锁 + MVCC 管并发，
  一致性 C 不是某一种技术，是另外三个加上应用约束共同的结果。答这句比硬编一个机制稳。
- **"幻读锁不住的行"这句是钥匙**。不可重复读针对已存在的某行，幻读针对符合条件的行集；
  你锁不住一条还不存在的数据，所以只能锁间隙。间隙锁为什么存在，从这里推出来，不用背。
- **RC 和 RR 的 MVCC 机制完全一样，只差快照什么时候拍**。RC 每条 select 都新建 ReadView，
  RR 只在第一条 select 建一次然后复用。所谓"可重复读"，本质就是"整事务共用一张照片"。
  另外 `begin` 不建视图，第一条 select 才建，`with consistent snapshot` 才是立刻建。
- **update 一定是当前读，这是个翻车点**。RR 里你快照看到 100，别人改成 200 提交了，
  你再 update 减 50，是在 200 上减的。这是正确的（否则丢更新），但和直觉不一样。
- **RR 解决幻读是两套办法**：快照读靠 MVCC（新插入的行 trx_id 太大，版本链里不可见），
  当前读靠 Next-Key Lock（把间隙锁住，插不进来）。答一半都不完整，
  也正好解释了为什么 RC 没间隙锁所以当前读有幻读。
- **间隙锁三个条件要同时满足**：RR 级别 + 当前读 + 走索引。
  没索引就退化成锁全表所有行和间隙，等于锁表。
- **间隙锁之间互不冲突**，冲突的是插入意向锁。它们防的是同一件事（插入），
  所以能共存；死锁也大多从这里来。
- **意向锁不是锁数据的**，是表级"挂牌"，让加表锁的人不用逐行扫一遍确认。
  IS 和 IX 互不冲突，只和表级 S/X 撞。
- **InnoDB 不预防死锁，只检测**：等有环就挑 undo 少的那个回滚，外加 50 秒超时兜底。
  排查看 `show engine innodb status` 的 LATEST DETECTED DEADLOCK。
- **长事务的害处不是"慢"，是拖着老 ReadView 不放** → 所有更晚的版本都得留在 undo 里，
  undo 一直膨胀。`set autocommit=0` 忘了提交是最常见来源。
