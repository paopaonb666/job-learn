### 1. 进程和线程的差别，本质上是"换不换地址空间"

进程是资源分配的基本单位（独立地址空间、fd 表、信号处理），线程是 CPU 调度的基本单位，
同一进程的线程**共享**堆、全局变量、文件描述符，**私有**栈、寄存器、程序计数器、TLS。

线程切换快就快在**不用换页表**：进程切换要换 CR3 寄存器指向新的页目录，
一换 TLB 里缓存的地址映射基本全废，之后一段时间每次访存都要重新走多级页表，这个代价非常大。
线程切换地址空间不变，TLB 大部分还能接着用。
另外进程切换还要切内核栈、刷新一些 per-process 的缓存（比如 ASID）。

一句话记住：**线程切换省的是"地址空间 + TLB"，不是"寄存器保存/恢复"**——后者两者都要做，开销差不多。

### 2. 僵尸进程 vs 孤儿进程，别搞反

- **僵尸进程**：子进程先死，父进程没 `wait()` 收尸。进程主体资源已经释放了，
  但内核还留着一条 PCB 记录（存退出码、耗时等），占一个 PID。
  **杀不掉**——`kill -9` 对已经死掉的进程没意义。清法是杀掉父进程，让 init/PID 1 接管后回收，
  或者父进程里注册 `SIGCHLD` 处理函数调 `waitpid(-1, ..., WNOHANG)` 循环收（循环很关键，
  SIGCHLD 是不可靠信号，多个子进程同时退出可能只通知一次）。
- **孤儿进程**：父进程先死，子进程被 init/PID 1 收养，正常跑完正常收尸，**没有危害**。

### 3. 调度算法：多级反馈队列为什么是"现实最优解"

FCFS 对长作业友好但短作业要等死（护航效应）；SJF 平均等待时间最优但长作业会饿死、
而且要预知运行时长（实际只能靠历史值指数平滑预测）；RR 公平但时间片设小了切换开销大、
设大了退化成 FCFS；纯优先级调度低优先级会饿死。

**多级反馈队列（MLFQ）** 把这几家的优点拼起来了，核心三条规则：

1. 多个队列，优先级从高到低，**高优先级队列时间片更短**
2. 新进程进最高级；**用完了当前级的时间片就往下掉一级**（长作业自然沉底）
3. 等待/IO 密集的进程会停在高级别（因为它总是没用完时间片就阻塞了），
   交互式任务响应快 —— 这就是它不需要预知运行时长也能近似 SJF 的原因

再加一条防饿死的：**定期把全部进程重新拉回最高级（priority boost）**。
Java 线程池里那种"长任务占着线程不动"的问题，思路上跟这个是一样的病。

### 4. 虚拟内存解决的是"隔离"，不只是"内存不够"

三个作用，重要性依次递减：

1. **隔离与安全**：每个进程看到的是从 0 开始的连续虚拟地址空间，A 进程根本没法访问 B 的内存
   （页表里没有映射），一个进程崩溃不会带崩别人
2. **让程序能超过物理内存**：配合页面置换，把暂时不用的页换到磁盘，
   程序以为自己有几个 G 的连续空间
3. **简化链接和加载**：每个程序的链接地址都是固定的（比如代码段都从同一个虚拟地址开始），
   不用关心物理内存里哪里有空位

代价是一次访存变成两次（先查页表拿物理地址，再访存），所以有了 **TLB** 缓存页表项。
TLB 命中率是这个方案能不能跑的关键，命中率一掉性能雪崩。

### 5. 分页 vs 分段：一个是物理视角，一个是逻辑视角

| | 分页 | 分段 |
| --- | --- | --- |
| 划分依据 | 物理，固定大小（4KB） | 逻辑，按代码段/堆/栈，长度不定 |
| 用户可见 | 不可见，OS 自己干的 | 可见，程序里要指定段号 |
| 碎片 | 内部碎片（最后一页用不满） | 外部碎片（段之间夹缝） |
| 目的 | 提高内存利用率、便于换入换出 | 方便共享与保护（代码段只读共享） |

现在的 x86-64 基本是**纯分页**，段寄存器还在但都设成基址 0，等于绕过分段。
教材里的"段页式"是先分段再在段内分页，结合了两者优点，但也带来了多一层地址转换。

### 6. 手撕 LRU：哈希表 + 双向链表，记住"为什么必须是双向"

要 O(1) 查询 + O(1) 更新顺序，只有一个组合：**HashMap 定位节点 + 双向链表维护访问顺序**。

- 单向链表不行：`get` 命中后要把节点移到头部，需要拿到前驱节点的指针，
  单链只能从头遍历找前驱，退化成 O(n)。用双向链表拿到节点本身就能把自己摘下来。
- 自己实现时用一个**伪头 + 伪尾**哨兵节点，可以省掉所有 head/tail 为空的边界判断。
- `LinkedHashMap` 就是这么干的，开 LRU 只要 `accessOrder=true` 并覆写
  `removeEldestEntry`，它自带的 `afterNodeAccess` 已经把"移到尾部"做好了。

**为什么真实 OS 不用严格 LRU**：维护精确访问顺序的硬件代价太高，
实际用的是 **Clock / 改进 Clock（二次机会）** 这种近似算法——
给每个页框一个访问位，缺页时扫一圈，访问位为 1 就清零跳过，为 0 就换出，
相当于"最近没被访问过就淘汰"的一个廉价近似。

### 7. 抖动（thrashing）：为什么加内存反而可能更卡

进程频繁访问的页（工作集）大于分配给它的物理页框数时，
刚换出的页马上又要换进来，刚换进来的又要被换出，**CPU 时间全花在缺页中断和磁盘 IO 上，
CPU 利用率反而暴跌**。

判断信号：CPU 利用率很低，但磁盘 IO 疯狂。
解法不是加进程，而是**降低多道程序度**（把一些进程挂起，把页框让给别的进程），
或者用工作集模型给每个进程分配足够的页框。
这个现象在 MySQL / Redis 上也有对应物：buffer pool 太小 + 随机访问 = 缓存命中率雪崩。

### 8. select / poll / epoll：差距不在"一次能监听多少"

| | select | poll | epoll |
| --- | --- | --- | --- |
| 结构 | fd_set 位图 | 数组 | 内核红黑树 + 就绪链表 |
| fd 数量 | 有上限（FD_SETSIZE 1024） | 无上限 | 无上限 |
| 每次调用 | 要把整个集合从用户拷到内核 | 同左 | 只注册一次，之后不用拷 |
| 找就绪 fd | 返回后要 O(n) 遍历全部 | 同左 | 直接拿到就绪链表，O(1) 数量级 |

**epoll 真正快在哪三件事**：

1. 用 `epoll_ctl` 把 fd 一次性注册进内核红黑树，`epoll_wait` 不用每次重传全部 fd（省掉重复拷贝）
2. 就绪的 fd 被内核回调挂到**就绪链表**上，`epoll_wait` 直接返回这个链表，
   复杂度跟"就绪数量"相关而不是"监听总数"——这是 C10K 下差距最大的一点
3. 用 mmap 共享一块内存传就绪事件，省一次内核到用户的拷贝

**为什么用红黑树不用哈希表**：fd 总数虽然大但相对固定，红黑树的 O(log n) 完全够用；
更关键的是红黑树在插入删除时**不需要 rehash**（哈希扩容要重建整表，会造成延迟毛刺），
而且遍历有序、内存占用可控、不会有哈希冲突攻击的问题。

### 9. LT 与 ET：ET 为什么必须配非阻塞

- **LT（水平触发，默认）**：只要缓冲区里还有数据，每次 `epoll_wait` 都会通知你。
  好处是**漏读不会丢事件**，这轮没读完下轮还会提醒，编程简单。
- **ET（边缘触发）**：只在**状态发生变化**的那一瞬间通知一次，比如从"没数据"变成"有数据"。
  通知次数少、效率高，但**你必须一次把缓冲区读干净**，
  没读完剩下的数据不会触发第二次通知，就永远卡在那里了。

所以 ET 模式下的标准写法是：`while (true) { n = read(fd, buf, sizeof buf); if (n < 0 && errno == EAGAIN) break; }`
——**必须配非阻塞 fd**，如果 fd 是阻塞的，最后一次 `read` 时缓冲区已经空了，
线程会直接阻塞在那里，整个事件循环就死了。Netty 的 NioEventLoop 就是这个套路。

### 10. 零拷贝：sendfile 到底省了什么

传统"读文件 + 发网络"一次要走的路（以 `read()` + `write()` 为例）：

1. DMA：磁盘 → 内核缓冲区
2. CPU 拷贝：内核缓冲区 → 用户缓冲区（第一次上下文切换回来了）
3. CPU 拷贝：用户缓冲区 → 内核 socket 缓冲区（又切回内核）
4. DMA：socket 缓冲区 → 网卡

**4 次上下文切换 + 2 次 CPU 拷贝 + 2 次 DMA 拷贝**，其中第 2、3 步的 CPU 拷贝是纯浪费——
数据根本没在用户态被加工过。

- `mmap` + `write`：省掉第 2 步，用户态和内核共享映射，还是 1 次 CPU 拷贝
- **`sendfile`**：第 2、3 步全省，数据直接在内核里从文件缓冲区流向 socket，
  **只剩 1 次 CPU 拷贝**（buffer → socket）；如果网卡支持 SG-DMA，
  连这次都能省（只传描述符），变成真正的"零 CPU 拷贝"

对应到 Java：`FileChannel.transferTo()` 底层就是 sendfile，
Kafka 之所以能把磁盘读做得飞快，靠的就是这个 + 顺序写 + page cache。
