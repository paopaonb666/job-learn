### 1. 三次握手为什么不能是两次：本质是"双向确认 + 防历史连接"

两次握手（客户端 SYN，服务端 SYN+ACK 直接建立）缺的是**客户端对服务端的确认**。
握手要确认的是四件事：客户端能发、服务端能收、服务端能发、客户端能收。
两次握手只证明了前三件，服务端无从知道自己的 SYN+ACK 有没有被收到，
只能"先分配资源建连接再说"，于是就埋了一个坑：

**历史连接问题**。客户端发了一个 SYN，网络堵住了没到，超时重传一个新的 SYN 建立了连接、
传完数据关闭了；这时那个**旧的 SYN 姗姗来迟**到服务端。两次握手下服务端收到就直接建连接、
分配缓冲区，白等一个根本不会发数据的客户端。三次握手下服务端回 SYN+ACK，
客户端发现自己要的序号对不上（这是旧连接的），直接回 **RST** 把连接掐掉，资源不用浪费。

所以那句"为了确认双方的收发能力正常"是对的，但更值钱的那半句是**让客户端有最后一次否决权**。

顺带：为什么不用四次？因为服务端的 ACK 和 SYN 可以合并在一个报文里发（都是服务端→客户端），
合并后就是三次，没必要拆。

### 2. 四次挥手为什么是四次，TIME_WAIT 为什么要等 2MSL

TCP 是全双工的，两个方向要**分别关闭**：

1. 主动方发 FIN —— "我不发了"（但还能收）
2. 被动方回 ACK —— "知道了"
3. 被动方把剩下的数据发完，再发自己的 FIN —— "我也不发了"
4. 主动方回 ACK

第 2 步和第 3 步**通常合并不了**，因为被动方收到 FIN 时，可能还有数据没发完，
ACK 必须立刻回（不然对方会超时重传 FIN），而 FIN 得等数据发完才能发。
所以中间有个"半关闭"的状态，这就多出来一次，变成四次。

**TIME_WAIT 等 2MSL（报文最大生存时间 ×2）有两个作用**，缺一不可：

1. **可靠地终止连接**：最后那个 ACK 可能丢，丢了对方会重发 FIN。
   如果不等直接关，收到重发的 FIN 时已经没有连接状态了，只能回 RST，
   对方会认为连接异常终止。等 2MSL 就能重发这个 ACK。
2. **让旧连接的残余报文在网络中消散**：不然这些迷途的报文可能被后面
   **复用了同一个四元组（源 IP:源端口, 目的 IP:目的端口）的新连接**收到，数据就串了。

**服务器大量 TIME_WAIT** 一般说明是服务器主动关连接（比如短连接的 HTTP 服务，
或者 Nginx 作为客户端去连上游）。解法：让对端主动关（`keepalive` 复用连接是最根本的）；
调 `net.ipv4.tcp_tw_reuse=1` 让 TIME_WAIT socket 可被新连接复用（要开 `tcp_timestamps`）；
`SO_LINGER` 强制关是**下下策**，会直接发 RST，把可靠的四次挥手变成异常终止。

### 3. TCP 的可靠性不是一个机制，是六个机制叠出来的

| 问题 | 机制 |
| --- | --- |
| 数据被改了 | 校验和 |
| 数据乱序 / 重复 | 序号 |
| 数据丢了（发送方不知道） | 确认应答 ACK |
| ACK 也丢了 | 超时重传（RTO 动态算，不是固定值） |
| 一个一个发太慢 | 滑动窗口（连续发一批，累计确认） |
| 发太快把网络打爆了 | 拥塞控制 |

单独看每一个都不新鲜，TCP 厉害在这些东西能配合起来，还都在同一个报文头里表达完。
**序号的语义是"我这个报文第一个字节的编号"，确认号是"我期望你下个字节的编号"**——
这一点想清楚了，滑动窗口和快重传就都顺了。

### 4. 流量控制 vs 拥塞控制：一个看接收方，一个看网络，别混

- **流量控制**是端到端的，怕的是**接收方处理不过来**。接收方在报文头的窗口字段里
  告诉发送方"我还能收多少"，发送方据此调整。窗口变成 0 时发送方停发，
  然后定时发**零窗口探测报文**去问，不然双方会死锁（窗口更新的 ACK 丢了就永远卡住）。
- **拥塞控制**是全局的，怕的是**网络链路堵了**。发送方自己猜网络状况，
  维护一个拥塞窗口 cwnd，最终发送量取 `min(接收窗口, cwnd)`。

### 5. 拥塞控制四步：慢启动、拥塞避免、快重传、快恢复

- **慢启动**：cwnd 从 1 个 MSS 开始，每收到一个 ACK 就 +1，实际效果是**每轮 RTT 翻倍**（指数增长）。
  所以"慢启动"其实一点都不慢，慢的是起点。
- **拥塞避免**：cwnd 超过慢启动阈值 ssthresh 后，改成每轮 RTT +1（线性增长），
  从这里开始才叫"小心试探"。
- **快重传**：收到 **3 个重复 ACK** 就立刻重传丢失的报文，**不等超时**。
  为什么是 3 个？收到 1、2 个重复 ACK 可能只是乱序，3 个基本可以断定是丢了。
- **快恢复**：以前丢包会把 cwnd 直接打回 1 重新慢启动（太保守，一次丢包就把速度砍没）。
  快恢复改成把 ssthresh 砍半、cwnd 也砍半，然后直接进拥塞避免线性长。
  **理由**：能收到 3 个重复 ACK 说明后面的包还在正常传，网络其实没那么堵，
  没必要从头来。

### 6. 粘包拆包的根源：TCP 是字节流，没有"消息"这个概念

TCP 只保证字节按序到达，**不保留发送时的边界**。发送方 `write` 了几次、
接收方 `read` 到几次，没有任何对应关系。真正的成因：

- **粘包**：发送方 Nagle 算法把小包攒起来发；或者接收方应用层没及时读，数据在内核缓冲区里堆着
- **拆包**：一个包超过 MSS（一般 1460 字节）被拆；或者超过接收窗口被拆

解法本质上都是**在应用层自己定义边界**，就三种：

1. **固定长度**（简单但浪费空间）
2. **分隔符**（比如 `\r\n`，缺点是正文里要转义）
3. **长度字段 + 正文**（最常用）：头部固定几个字节写长度，先读长度再读这么多字节。
   Netty 的 `LengthFieldBasedFrameDecoder`、Dubbo、Redis 的 RESP 协议都是这个思路。

顺带纠正一个常见误解：**UDP 不会粘包**，因为它保留了消息边界，一次 `sendto` 对应一次 `recvfrom`。

### 7. HTTP/1.1 → 2.0 → 3.0：每一代解决的都是上一代的队头阻塞

- **1.0**：每个请求一个 TCP 连接，用完就关。慢启动都还没跑完就结束了。
- **1.1**：长连接 `Connection: keep-alive` + 管道化（pipeline）。
  但**队头阻塞**没解决：请求必须按发出顺序返回，第一个卡住后面全等着。
  浏览器实际的土办法是开 6~8 个 TCP 连接并发。
- **2.0**：**多路复用**——一个 TCP 连接上跑多个 Stream，每个请求一个 Stream ID，
  帧可以乱序发、乱序回，谁先好谁先回。**队头阻塞在应用层解决了**。
  外加 HPACK 头部压缩、二进制分帧。
  **但 TCP 层的队头阻塞还在**：TCP 是严格按序的字节流，丢一个包整个连接都要等重传，
  所有 Stream 一起卡。
- **3.0 / QUIC**：干脆把传输层换成基于 UDP 自己实现的 QUIC，
  每个 Stream 独立做可靠传输，**一个流丢包不影响其他流**，
  还顺便把 TLS 握手和连接建立合并（1-RTT，会话复用 0-RTT）、支持连接迁移
  （换 WiFi 时 IP 变了连接不断）。

### 8. HTTPS 握手：非对称加密换钥匙，对称加密传数据

为什么不全程非对称？因为**非对称（RSA/ECDHE）计算慢几个数量级**，只用它来安全地协商出
一个会话密钥，后面全部走对称加密（AES）。TLS 1.2 握手大致是：

1. 客户端 `Client Hello`：支持的 TLS 版本、密码套件列表、随机数 R1
2. 服务端 `Server Hello`：选定的套件、随机数 R2、**证书链**（含公钥）
3. 客户端**校验证书**（见下），取出公钥，生成第三个随机数 **Pre-Master**，
   用公钥加密发过去（ECDHE 则是交换公钥参数，双方各自算出同一个密钥）
4. 双方用 R1 + R2 + Pre-Master 各自算出同一个**会话密钥**，之后全走对称

**防中间人靠的是 CA 信任链，不是加密本身**。浏览器内置了一批根 CA 公钥，
用根 CA 的公钥验中级 CA 的证书签名，再逐级往下验到服务器证书，
同时检查**域名是否匹配、是否在有效期内、是否被吊销（CRL/OCSP）**。
中间人拿不到 CA 私钥就伪造不出能被验证通过的证书；
就算诱导用户装了他的根证书（抓包工具就是这么干的），
服务端也可以靠**证书固定（Certificate Pinning）**再挡一道。

三个随机数的意义：**Pre-Master 只有双方知道，R1/R2 是明文的，混在一起是为了让每次会话的密钥都不一样**，
防止重放和密钥复用。TLS 1.3 精简到 1-RTT，砍掉了 RSA 密钥交换（只留前向安全的 ECDHE）。

### 9. GET 和 POST：差别在语义，不在"长度限制"和"安全性"

按 RFC 的语义：**GET 是安全且幂等的（只查询，不改服务器状态），POST 不是**。
由此推导出一堆实际差异：

- GET 可以被缓存、能被收藏为书签、会留在浏览器历史里；POST 不会
- GET 参数在 URL 里，POST 在 body 里（所以 GET 不适合传敏感信息——不是因为"更安全"，
  只是它会被到处记录）
- **"GET 有长度限制"是错的**：HTTP 规范没有任何长度限制，
  那个 2KB/8KB 是**浏览器和服务器对 URL 长度的实现限制**
- POST 的 body 可以很大、支持二进制；GET 只能 URL 编码

反过来说，用 GET 去下单、用 POST 去查询，都是能用但**违反语义**的写法，
被问到时把这个区别说清楚比背条条强。

### 10. 输入 URL 到页面显示：按"先找 IP、再建连接、再要资源"这条主线串

1. **URL 解析**：协议、域名、端口（http 默认 80 / https 默认 443）、路径
2. **缓存判断**：浏览器强缓存（`Cache-Control: max-age`）命中就直接用，
   **连请求都不发**；否则进协商缓存（`If-None-Match` / `If-Modified-Since`，
   命中返回 304）
3. **DNS 解析**：浏览器缓存 → 操作系统缓存 / hosts → 本地 DNS 服务器
   （**递归查询**，它去帮我们做**迭代查询**：根域 → 顶级域 → 权威域）
4. **TCP 三次握手**（HTTPS 还要叠一层 TLS 握手）
5. **发 HTTP 请求**，服务器处理并响应，浏览器收响应
6. **解析渲染**：HTML → DOM 树，CSS → CSSOM 树，合成 Render Tree → 布局 → 绘制。
   遇到 `<script>` 会**阻塞解析**（所以要 `defer` / `async`）
7. **连接复用或关闭**（`keep-alive` 就留着给后续请求用）

面试说的时候抓住这条主线就够了，每个环节都能再往下挖一层（比如 CDN、负载均衡、
反向代理在哪一步介入），别一上来就掉进细节里出不来。
