### 1. 为什么是 B+ 树：赢在"一个页能塞多少 key"

面试官问这个，答"矮胖、范围查询快"只是结论，要把链条说完整：

InnoDB 一页默认 16KB，索引项是 `key + 指针`。B 树**每个节点都带完整行数据**，
一页塞不下几个；B+ 树非叶子节点**只存 key 和指针**，不存数据，
一页能塞上千个 key，所以**扇出高、树更矮**。三层 B+ 树就能存两千万行，
意味着查一条数据最多 3 次磁盘 IO。这是最硬的一条理由。

另外两条：

- **范围查询**：B+ 树叶子节点之间有双向链表，找到起点后顺着扫就行；
  B 树要中序遍历，来回跨层，全是随机 IO。
- **查询次数稳定**：B+ 树所有数据都在叶子，任何查询都要走到叶子层，
  IO 次数可预测；B 树可能在根节点就撞上，快慢不一，不好评估。

### 2. 那为什么不是 Hash，不是二叉搜索树

- **Hash**：等值查询 O(1)，但**只支持等值**。范围、排序、前缀匹配全废，
  哈希冲突严重了还得拉链退化成遍历。MySQL 的 Adaptive Hash Index 是 InnoDB
  自己给热点页加的，**用户建不了**，也从侧面说明它只能当配菜。
- **二叉搜索树**：极端情况退化成链表（有序插入时）；就算红黑树/AVL 平衡了，
  也是**一个节点一条记录，树太高**，而每一次往下走一层就是一次磁盘 IO。
  索引结构的敌人从来不是"比较次数"，是**IO 次数**，所以必须多路。

一句话收尾：**B+ 树是"多路 + 数据只在叶子 + 叶子连成链"这三件事一起起作用。**

### 3. 聚簇索引、二级索引、回表：一个概念串出两个实践结论

InnoDB 里**主键索引就是数据本身**——主键 B+ 树的叶子节点挂着整行数据，这叫聚簇索引。
二级索引（普通索引、唯一索引）的叶子节点挂的是**主键值**，不是行地址。

所以走二级索引查整行，要**扫两棵树**：先在二级索引树里拿到主键，
再拿主键去主键树里捞数据，第二次就叫**回表**。

顺着这个概念能推出两个很有用的实践结论：

- **主键要尽量小**。主键越大，每个二级索引的叶子节点就越大，所有二级索引一起膨胀。
  这也是为什么推荐自增 BIGINT 而不是长字符串。
- **主键要自增、别用随机值（比如 UUID）**。B+ 树叶子是有序的，
  随机主键插入会频繁插到已有页中间，触发**页分裂**、产生碎片；
  自增主键永远往最右边追加，满了新开一页，几乎不折腾。

> 顺带说清楚一个常被问混的点：MyISAM 是**非聚簇**的，索引叶子存的是数据文件地址，
> 主键索引和二级索引没有本质区别，所以 MyISAM 可以没有主键，InnoDB 不行
> （你不建它也会挑一个非空唯一列，再挑不出来就造个 6 字节的隐藏 rowid）。

### 4. 覆盖索引：把回表这一步直接省掉

二级索引上如果**已经带了你要查的所有字段**，就不用回表了，
这叫覆盖索引，`EXPLAIN` 里表现为 `Extra: Using index`。

实际用法：`select id, name from user where name = 'x'`，
如果只有 `(name)` 索引，其实 name 索引的叶子上已经有 name 和主键 id 了，
天然覆盖；但 `select * ` 就一定回表。

这也是为什么有人会刻意建看起来"冗余"的联合索引 `(a, b)`——
不为过滤，只为让 `select b where a = ?` 不回表。
代价是索引变大、写变慢，别滥用。

### 5. 最左前缀：不是规定，是 B+ 树排序的必然结果

联合索引 `(a, b, c)` 在 B+ 树里是**先按 a 排，a 相同再按 b 排，b 相同再按 c 排**。
所以：

- 查询条件里**没有 a**，就没法在这棵树里定位扫描起点，索引直接失效（全表扫或全索引扫）
- 有 a 没 b，能用上 a 这一截，b 及以后的过滤只能拿到数据后逐行判断
- **范围查询会截断后面的列**：`a = 1 and b > 10 and c = 5`，
  c 用不上。因为 a=1 确定的那段里 b 是有序的，但 b 变成范围之后，
  结果集里 c 就**不再有序**了，没法继续在树里定位

理解成"有序性的传递被范围查询打断"比死记"范围之后失效"要牢。

### 6. 索引失效的几种，按"有没有破坏有序性"来分

| 写法 | 为什么失效 |
| --- | --- |
| `where year(create_time) = 2026` | 对索引列套了函数，得逐行算完才知道值，有序性没了 |
| `where code = 123`（code 是 varchar） | **隐式类型转换**，等价于 `CAST(code AS INT)`，同上 |
| `like '%abc'` | 前缀不确定，没法在树里定位起点（`like 'abc%'` 是可以走索引的） |
| `where a = 1 or b = 2`，b 没索引 | or 里只要有一边走不了，引擎干脆全表扫 |
| 字段字符集/排序规则不一致（联表时） | 和类型转换一个道理 |

还有一种是**优化器主动放弃**：命中行数太多时（经验值 20%~30% 以上），
它会判断"回表那么多次还不如顺序扫全表"，于是选全表。
这不是索引失效，是优化器的成本决策——`EXPLAIN` 里看到 `possible_keys` 有值
但 `key` 是 NULL，多半就是这个。

### 7. 索引下推 ICP：把过滤从 Server 层下沉到存储引擎层

MySQL 5.6 之前，联合索引 `(name, age)` 查 `where name like '张%' and age = 10`：
存储引擎只能按 `name` 前缀定位到所有姓张的记录，
**每条都回表一次**，把完整行交给 Server 层去判断 age。

5.6 之后，存储引擎层会**先用索引里已经有的 age 字段过滤一遍**，
只对通过的那些去回表。回表次数从"所有姓张的"降到"姓张且 age=10 的"。

`EXPLAIN` 里 `Extra: Using index condition` 就说明用了 ICP。
注意它只对**联合索引中、没被用来定位但确实在索引里的那些列**有效
（索引里没有的字段没法下推）。

### 8. 联合索引字段顺序怎么定

网上说"区分度高的放前面"是个粗糙的说法。更准的规则是三条，按优先级：

1. **等值查询的列放前面，范围查询的列放最后**（因为范围会截断后面的）
2. **能复用的优先**：`(a, b)` 已经能当 `(a)` 用，所以没必要再单独建 `(a)`，
   建之前先看能不能合并进现有的联合索引
3. 前两条都差不多时，再比**区分度**，区分度高的靠前，能让第一次过滤筛掉更多行

举个实际点的：订单表经常 `where user_id = ? and status = ? order by create_time desc`，
建 `(user_id, status, create_time)`——前两个等值定位，最后一个既参与排序、
又省掉了 `filesort`。

### 9. Change Buffer：二级索引写慢的药，也是"别滥用唯一索引"的理由

更新一条记录时，如果它对应的**二级索引页不在内存里**，正常做法是先把页读进来再改，
一次随机 IO 就搭进去了。

Change Buffer 的做法是：**非唯一二级索引**的修改先记在内存里的一块缓冲区，
不管那个页在不在，等以后真的要读这个页时，再把缓存的修改合并进去（merge）。
对"写多、写完短期内不读"的场景（比如日志表、流水表）收益很大。

关键限制：**唯一索引享受不到**。因为唯一索引必须先读出索引页去检查有没有冲突，
既然页都读进来了，就没必要再缓存了。所以才有一句实践建议——
**能用普通索引保证的业务唯一性，就别顺手加 UNIQUE**，
唯一索引换来的是每次写多一次磁盘读。（前提是你确实靠应用逻辑保证了唯一。）

redo log 也会记 change buffer 的操作，所以崩溃不丢。

### 10. 深分页为什么慢，延迟关联怎么救

`limit 1000000, 10` 慢，不是因为"limit 跳过了"这么简单：
MySQL 得先**扫描并回表 1000010 行**，把前 100 万行全部丢弃，只留 10 行。
回表那 100 万次随机 IO 才是真正的开销。

**延迟关联**的思路是把回表推迟到确定要的那 10 行之后：

```sql
select * from t
join (select id from t where status = 1 order by id limit 1000000, 10) x
on t.id = x.id;
```

子查询里只用覆盖索引拿 id（不回表，顺序扫索引），
外层拿 10 个 id 去主键树捞，回表次数从 100 万降到 10。

如果还能拿到上一页的最大 id，用**游标分页**更好：
`where id > 上一页最大id order by id limit 10`，
一次 IO 都不浪费，代价是不能跳页。

### 1. ACID 四个字母，各自背后站着谁

别四个字母一起背，拆开对应到具体机制：

- **原子性 A** → **undo log**。改一行之前先把旧值记下来，回滚就是照着 undo 逆向改回去。
  注意 undo 是**逻辑日志**：insert 对应 delete，update 对应反向 update，不是物理页面的镜像。
- **一致性 C** → 这个不是某一种技术，是**前面三个合起来的结果**。
  面试官问"C 靠什么保证"，答"原子 + 隔离 + 持久 + 应用层的约束（主键、唯一、外键）共同保证"，
  比硬编一个机制要稳。
- **隔离性 I** → **锁 + MVCC** 两套机制配合。写写冲突用锁，读写冲突用 MVCC 让读不阻塞写。
- **持久性 D** → **redo log**。改数据只改内存里的页（Buffer Pool），
  redo 先落盘；就算断电，内存脏页丢了，重启后也能按 redo 重放。这就是 WAL：**先写日志再写数据**。

一句话串起来：**undo 管回滚，redo 管崩溃恢复，锁和 MVCC 管并发**。

### 2. 三种"读错了"的现象，得分清是谁的锅

| 现象 | 描述 |
| --- | --- |
| 脏读 | 读到别人**没提交**的修改，人家一回滚你就读到了不存在的数据 |
| 不可重复读 | 同一行，事务内**读两次不一样**，因为中间别人提交了一次 update |
| 幻读 | 同样的**范围条件**，事务内读两次**行数不一样**，因为中间别人 insert 了 |

很多人只会背"不可重复读是改，幻读是增删"。更准的说法是：
**不可重复读针对已存在的某一行，幻读针对的是"符合某个条件的行集"**。
所以解决幻读光靠给行加锁不够——你锁不住**还不存在**的那一行，得把**间隙**也锁住。
这一句想通了，后面间隙锁为什么存在就不用背了。

### 3. 四种隔离级别：一条递进的线

读未提交（啥问题都有）→ 读已提交 RC（解决脏读）→ 可重复读 RR（解决脏读 + 不可重复读）
→ 串行化（全部解决，靠加锁把并发彻底排掉）。

两个要注意的点：

- **InnoDB 的 RR 已经解决了幻读**，这是 MySQL 相对标准 SQL 的加强，
  别照着课本说"RR 下还有幻读"。
- 隔离级别越高，并发越差。MySQL **默认是 RR**，Oracle、PG 默认是 RC。
  互联网业务里把 MySQL 调成 RC 很常见：RR 下间隙锁范围大、死锁概率高，
  RC 下**没有间隙锁**（除了外键检查），并发更好，幻读问题靠业务逻辑或显式加锁兜住。

### 4. MVCC：一条版本链 + 一个快照

InnoDB 每行数据有两个隐藏字段：`trx_id`（最后改它的事务 ID）和 `roll_pointer`
（指向上一版本的 undo log）。每次 update，旧版本进 undo log，
新版本的 roll_pointer 指过去，于是**同一行连成一条版本链**。

读的时候生成一个 **ReadView**，里面记着"此刻有哪些事务还活着"。
顺着版本链往回走，一直走到**第一个我该看见的版本**为止：

- 版本的 trx_id == 我自己的事务 ID → 我改的，看得见
- 版本的 trx_id < 活跃事务里最小的那个 → 它早就提交了，看得见
- 版本的 trx_id 在活跃列表里 → 它还没提交，看不见，继续往回走
- 版本的 trx_id > 未来要分配的最大 ID → 它是我之后才开的，看不见

**这就是为什么"读不加锁、写不阻塞读"**：写的人改的是新版本，
读的人顺着链走找自己那一份，各看各的。MVCC 只在 RC 和 RR 下生效，
读未提交直接读最新，串行化直接加锁。

### 5. RC 与 RR 的差别：就是"快照什么时候拍"

同一条 SQL，两个隔离级别下 MVCC 机制完全一样，
**唯一区别是 ReadView 的生成时机**：

- **RC：每一条 select 都重新生成一个 ReadView**。
  所以别人在你两次查询之间提交了 update，你第二次就能看见 → 不可重复读。
- **RR：只有事务里第一条 select 生成 ReadView，后面一直复用**。
  相当于整个事务共用一张照片，后面怎么改都看不见 → 可重复读。

面试追问"RR 是怎么做到可重复读的"，标准答法就是这句：
**事务启动时拍一张快照，之后所有普通读都用这一张**。
（严格说是第一条 select 时才建，不是 begin 那一刻——
`begin` 只开事务不建视图，`start transaction with consistent snapshot` 才是立刻建。）

### 6. 快照读 vs 当前读：最容易翻车的一条

- **快照读**：普通 `select`，走 MVCC，不加锁，读的是历史版本。
- **当前读**：`select ... for update`、`select ... lock in share mode`、
  以及所有的 `insert / update / delete`。它们必须读**最新的已提交版本**，
  而且**要加锁**，否则会丢更新。

翻车点在于：**update 一定是当前读**。
事务 A 快照读看到余额 100，事务 B 把它改成 200 并提交了，
A 再 `update ... set money = 100 - 50`，A 是在**最新值 200 上**减的，不是它看到的 100。
这是对的（不然就丢更新了），但很多人以为"我在 RR 里看到的是 100，改完就是 50"。

### 7. RR 下怎么解决幻读：快照读和当前读是两套办法

- **快照读的幻读 → MVCC 解决**。事务启动时快照已定，
  别人后插的行 trx_id 比我大，版本链里直接被判为不可见，行数自然不变。
- **当前读的幻读 → Next-Key Lock 解决**。当前读必须看最新数据，MVCC 兜不住，
  只能靠把**间隙也锁住**，让别人插不进来。

所以标准答案是"**MVCC + 间隙锁**"，缺一半都不完整。
这也解释了为什么 RC 下（没有间隙锁）当前读会有幻读。

### 8. 三种行锁：Record、Gap、Next-Key

- **Record Lock**：锁住某一行本身。
- **Gap Lock**：锁住两条记录之间的**空隙**，不含记录本身。锁的是"不许往这里插"。
- **Next-Key Lock**：前两者合体，左开右闭的区间，**锁住行 + 它前面的间隙**。
  InnoDB 默认用的就是它。

间隙锁的触发条件，三条同时满足：

1. 隔离级别是 **RR**（RC 下基本没有）
2. 是**当前读**（for update / update / delete）
3. 走的是**索引**（没索引就退化成锁全表所有行和间隙，等于锁表）

关键认知：**间隙锁之间不冲突**。多个事务可以对同一个间隙加 gap lock，
因为它们防的是同一件事——插入。真正冲突的是**插入意向锁**和 gap lock 撞上。
这也是间隙锁容易造死锁的根源。

### 9. 意向锁：为了解决"我要锁表，得先逐行扫一遍吗"

事务 A 想加表锁，按规矩得确认表里**没有一行**被别的事务锁着，
难道要遍历每一行去查？意向锁就是给这个场景准备的"挂牌"：

- 事务要锁某些行之前，先在**表级**挂一个意向锁（IS 或 IX）
- 别人要加表级 S/X 锁时，只看一眼表上有没有意向锁就知道行不行，
  不用扫全表

所以意向锁是**表级锁**，但它不锁任何数据，只是标记"里面有行被锁了"。
IS 和 IX 之间互相兼容，只有和表级 S/X 锁才冲突。

### 10. 死锁：不是靠避免，是靠"让它发生然后快速处理"

InnoDB 的做法和 Java 里的思路不一样，它**不做预防，做检测**：

- **等待图检测**：发现环就挑一个回滚。挑谁？**回滚代价小的**
  （通常看 undo 量，也就是改得少的那个）。
- **超时兜底**：`innodb_lock_wait_timeout` 默认 50 秒，超时就放弃等待。
- **排查**：`show engine innodb status` 里的 `LATEST DETECTED DEADLOCK` 段，
  能看到两个事务各自持有什么、等什么、最后一句 SQL 是什么。

工程上的减少手段就三条：

1. **固定加锁顺序**（比如按 id 升序处理），环就形成不了
2. **事务尽量短、锁的行尽量少**，撞上的概率自然降
3. **把热点行的更新改成排队或 CAS**，比如库存扣减用
   `update stock set n = n - 1 where id = ? and n >= 1`，
   靠条件把并发串行化，不用显式加锁

### 11. 长事务：不是"跑得久"，是"拖着老视图不放"

长事务的危害清单：

- **老 ReadView 不能释放** → 所有比它晚的版本都得留在 undo log 里，
  undo 日志**持续膨胀**，rollback segment 占着不放
- **锁持有时间长** → 阻塞别人，死锁概率直线上升
- **主从延迟**、回滚耗时

自查方式：`information_schema.innodb_trx` 里找
`TIMEDIFF(now(), trx_started) > 60` 的就是可疑对象。

实践建议：把 `autocommit` 打开，别在事务里做 RPC、查缓存、等用户输入；
`set autocommit=0` 然后忘了提交，是长事务最常见的来源。
